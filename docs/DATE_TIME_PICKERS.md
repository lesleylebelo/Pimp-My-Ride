workshop quotation forms, customer requests, booking lists/details and Admin
forms. Vehicle model years, quotation validity in days, and completion estimates
in working days remain numeric fields. There are no existing workshop opening-hour,

## Shared API and platform behaviour

- `AppDatePicker`: `label`, `value`, `onChange`, `onBlur`, `disabled`,
  `minimumDate`, `maximumDate`, `error`, `helperText`, `clearable`.
- `AppTimePicker`: the same API, with `minimumTime` / `maximumTime`.
- Values and bounds are canonical strings (`YYYY-MM-DD` / `HH:mm`). Empty is
  `''`. Components are controlled: selections call `onChange`; the form owns state.
- `AppDateTimeField` shares labels, validation feedback, optional clearing, theme
  styling and range checks. There is no combined timestamp field in the existing
  forms, so a third combined-value public component is unnecessary.
- Android uses the system calendar/time dialogs through the recommended
  imperative API, with 24-hour time, `Africa/Johannesburg`, explicit Select/Cancel,
  date limits and application-side time-range checks. Android's native time dialog
  does not enforce minimum/maximum times; rejected selections leave the value intact.
- iOS uses a themed system spinner inside a native modal, with a temporary draft
  committed only by **Use selection**. Cancel/back leaves the form value intact.
- Web uses HTML date/time controls with native browser calendar/time interfaces,
  keyboard entry/navigation, accessible names, described validation, native range
  attributes, themed surfaces and a 44 px picker trigger. `showPicker()` is optional;
  browsers without it retain their input's native keyboard/calendar affordances.
  Browser/OS locale controls the visible date order and 12/24-hour presentation;
  API values remain ISO calendar strings and 24-hour times. Browser popup appearance
  and Android dialog appearance follow the platform theme; app field surfaces use
  the selected PimpMyRide theme.
- Disabled fields block selection and optional clearing. Android cancellation,
  disabling, unmounting and external value changes invalidate pending callbacks.
  Invalid saved values display validation feedback without crashing or automatic
  conversion. Out-of-range selections never overwrite the controlled value.

One dependency was added: `@react-native-community/datetimepicker` **9.1.0**,
matching the installed Expo 57 `bundledNativeModules.json` recommendation and the
[Expo SDK 57 reference](https://docs.expo.dev/versions/v57.0.0/sdk/date-time-picker/).
Its only dependency was already present. The
[upstream API documentation](https://github.com/react-native-datetimepicker/datetimepicker)
documents Android dialogs, `timeZoneName`, cancellation, and native range limitations.
Web resolution uses a separate adapter, so the native package is excluded from
the web dependency graph.

## Timezone, validation and security

Date-only values never pass through device-local midnight or `toISOString()` on
a local Date. Native picker values are anchored at noon in SAST; native results
are read with an explicit UTC+02:00 calendar shift. SAST has no daylight-saving
adjustment. `Africa/Johannesburg` is passed to native pickers and used for calendar
display. Tests exercise UTC, Los Angeles, Auckland and Johannesburg, leap days,
midnight, and times whose UTC timestamp falls on the previous date.

The Workshop preferred-date display previously parsed a bare calendar string
with the device timezone. It now uses the shared explicit-SAST calendar formatter,
preventing a previous-day display west of UTC. Existing booking display keeps its
saved date/time and explicit SAST label; no saved record is migrated or rewritten.

`bookingConfirm` still receives only `{id, appointmentDate, appointmentTime}`.
The existing backend validates strict dates/times and a future SAST instant,
checks workshop ownership, role, status and account eligibility in its transaction,
and stores the existing `appointmentAt` timestamp using UTC+02:00. It rechecks the
future instant before writing. Request create/update still authoritatively validate
the preferred South African date. Existing receipt/idempotency behaviour is intact.
No backend, authentication, permission, payment, email or AI code was changed.

## Release assessment and remaining limits

The web change is ready for release review based on the checks above. A new
Android/iOS native binary is required to include the added native module; this
cannot be delivered solely as a JavaScript update to an older binary. Android SDK
tools are present, but `adb devices` found no connected device and
`emulator -list-avds` found no configured emulator. Native callbacks and flows are
covered with mocks; a rebuilt-device smoke test of opening, selecting, cancelling,
rotation/back behaviour and app/system theme differences remains required before
signing off the Android release. iOS runtime verification was not available.

These results are not an unconditional application-wide production-readiness
sign-off. Unrelated release limitations already documented elsewhere remain outside
this change.
